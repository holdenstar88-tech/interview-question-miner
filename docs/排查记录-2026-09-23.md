## 本轮修复与复测

1. **分页遗漏已修复。** 牛客 `/discuss` 返回的公开 HTML 含 `.el-pager` 下一页链接，原发现器只跟进 XML。本轮添加同主机 HTTPS 分页、有界页数、循环去重，保持默认 3 页和每来源 40 次 HTTP 总上限。新发现器真实运行读到 3 页、648 个页面链接、95 个文章链接，去重得到 47 个候选；含 robots/重定向共 5 次 HTTP 请求。60 天是收录窗口，不保证推荐列表覆盖过去 60 天全部帖子。
2. **临时解析失败可以恢复。** 正文缺失/过短/发帖时间缺失进入持久化 retryable 队列，默认每帖每天最多 3 次解析抓取，间隔 30 秒；次数/冷却保存在 SQLite，重启不会重置。下次运行会继续复查已到期候选，不依赖推荐列表再次出现。真实烟测限 4 个候选：入口页此次又返回空列表，但从旧重试队列恢复 3 篇新文章，另 1 篇经过两次正文缺失、第三次请求取到正文，确认是已存原帖。共 6 次文章请求，成功新增 3、已见 1、临时解析失败 2，计数吻合；不再把临时缺正文锁死为当日永久跳过。
3. **只认原帖发帖时间。** 实际 feed 原帖字段是 `createdAt`，旧程序整页搜索的首个 `createTime` 来自相关推荐。现在以 URL ID 匹配 `prefetchData[*].contentId` 和 `ssrCommonData.contentData.id/uuid`，只取该原帖的 `createdAt/createTime`。评论、推荐、编辑时间、正文面试日期和整页任意 time/meta 都不能提供牛客发帖时间。真实 feed 验证得到原帖日期 `2026-09-11T18:51:18+08:00`。
4. **先诊断模型，再改善超时与重试。** 本地已配置的中转与 `gpt-5.6-sol/high` 在真实失败帖上复测：首次安全诊断 39.08 秒返回合法 JSON，2267 字符，finish_reason=stop，usage=4423 tokens。新抽取器完整复测 84.50 秒返回合法 Schema，2244 字符，usage=3724 tokens（reasoning=855），10 道题，confidence=0.94，原文证据检查无问题。84.5 秒接近原来的 90 秒，因此将被 Git 忽略的本地 `llm.timeout` 调至 180 秒；保留最多两次重试，分别等待 5/10 秒，明确的鉴权/参数错误不重复请求。没有把失败归因为额度不足，也没有假定外部服务从此不会波动。
5. **日志可对应损耗环节。** 分开发现失败和文章失败，避免异常内外双计；记录发现页/分页/空页、候选、实际 HTTP/状态码/重试、解析尝试、收录/已见/时间窗外/原因分类、冷却/限次及未处理候选。粗筛保存未命中面试词、未命中岗位词、正文缺失的原因。模型日志只记录耗时、finish_reason、字符数、tokens、JSON 错误位置、Schema 路径，不记录密钥、正文、提示词或模型字段值。
6. **日期口径完整统一。** 采集窗口、月度归档、查询、频次 first/last_seen、高频榜及模板全部按 `publish_time`。轮次日期仅作为内容字段保留。v3 升级自动备份旧 SQLite；旧牛客记录的时间先标为未验证，保留 raw/抽取内容，重新抓取确认后才能进入抽取/输出，避免把旧的错误日期继续用于新版输出。烟测后 SQLite integrity_check=ok，外键错误为 0。

## 修复前的问题证据

1. **发现范围窄，而且页面响应不稳定。** 配置只从牛客 `/discuss` 开始；发现器会继续读取 XML 链接，但不跟进 HTML 列表分页。`max_discovery_pages=3` 并不意味着实际读了三页。第一次发现 16 个候选，随后全流程再次请求同一入口时只有 4 个页面链接、0 个文章候选。60 天是已发现文章的日期过滤窗口，不是已遍历过去 60 天全部文章的保证。应检查实际可用且 robots 允许的公开列表分页/RSS/站点地图，并把空发现页作为可诊断的来源状态。

2. **临时正文缺失会导致当天不再尝试。** 首次判正文缺失的 `/discuss/931694858605981696` 和 `/feed/main/detail/d7a08de80c19414893be0279be515314`，诊断复查均返回 HTTP 200 并出现现有解析器对应的正文节点。`Store.attempted_today()`（`pipeline/store.py:153`）不区分成功、永久跳过和临时失败，`collect.py` 会跳过当天所有已尝试 URL。应为临时失败设计有限次数、带冷却时间的重试；成功、付费、禁止访问等仍按各自规则处理，不无限重试。

3. **发帖时间解析存在误取评论日期的可能。** `pipeline/collect.py:69` 对整页选择第一个 `time[datetime]`，并在全 HTML 搜索第一个 `createTime`。已用模拟页面复现：文章没有发布日期、仅评论含时间，仍被接受并把评论时间当作发帖时间。这违反“只按原帖发布时间”的要求。应绑定文章主体/对应帖子 ID 的元数据，排除评论、推荐文章和用户注册时间；缺少可信原帖时间继续跳过。

4. **真实模型抽取失败的诊断信息不足。** 当前只能知道 JSON 解析失败，没有保留 finish_reason、响应长度、解析错误位置等信息，无法分辨空返回、截断或格式错误。应记录这些不含正文的元信息，为真实长文章增加兼容性验证，评估 90 秒超时是否适合中转服务的 high 推理模式；重试保持有界。本轮不把失败响应原因进一步猜测为额度或鉴权问题。

5. **损耗统计还不准确。** 已模拟复现一个文章 SourceUnavailable 异常，article_fetch_attempts=1，但 failures 同一原因=2；原因是 `pipeline/collect.py:311` 和 `:325` 内外两层重复累计。另 `pipeline/extract.py:203` 丢弃粗筛返回的具体原因，实际三条 filtered 记录的 error 均为空。应统一异常计数归属，分别保存未命中面试词、未命中岗位词和正文缺失的原因。本轮重新计算的三篇粗筛失败中，2 篇未命中面试词、1 篇未命中岗位词。

6. **日期规则说明及内部接口仍有旧逻辑。** 渲染主流程已按发布日期归档和排名，但 `templates/top.md.j2:5` 仍写“日期取明确面试日期，否则取发布日期”。`Store.questions_for_render(since=...)` 仍按 occurrences.event_date 过滤，而该字段仍优先保存面试日期；目前 render_all 没有传 since，当前输出不走这条旧筛选，但接口语义需要统一。离线榜单的部分测试仍只构造 event_date，不能充分验证“发表日期新、面试日期旧”的要求。

上述为修复前证据，本轮处理结果见第一节。虚拟环境入口仍建议在移动目录后重建；直接调用项目 `.venv/Scripts/python.exe` 与 `python -m pip` 可用。
